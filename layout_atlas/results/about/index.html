About Open Meta Maps

Two parts: a curated-structure Atlas from public community maps, and a layout optimisation pipeline that reuses matching geometry and completes the rest with Bézier connections.

Open Meta Maps is ELIXIR BioHackathon Europe 2026 Project 22 (Open Pathway Maps). Every reaction and metabolite of the uploaded GEM is drawn; stoichiometry and compartments are unchanged.

Map Generator: python3 project.py tool or ./start_tool.command. Examples: e_coli_core, iIT341, iMM904, iML1515. Viewer: pan, wheel/pinch zoom, minimap. Server exits when the last tab closes (~8 s); --keep-running disables that. Evaluate layouts with python3 project.py evaluate.

Cut windows are every stored module: each map is cut into breadth-first reaction windows of increasing size grown from many root reactions, so most windows nest inside larger windows of the same map. Small windows are kept intentionally because they match small models. Distinct structures are windows not contained in a larger window of the same source map (reaction set; node set for geometry-only windows) with at least 3 reactions, merged across sources by dedup key.

WikiPathways semantic modules live in open_core.sqlite; geometry-only windows ship as an extension for repository size. Both load by default. Dedup stats: docs/images/atlas/atlas_overlap.json.

The Atlas Browser tab searches these curated modules by EC, reaction, metabolite or model ID, source map and licence, and downloads selected modules as Escher JSON with a provenance/licence manifest (rebuild the search index with python3 tools/build_atlas_browser_index.py).

python3 project.py data export bundles the whole Atlas into one archive: Escher JSON per module, the same manifest and the third-party notices (--source, --licence and --all-windows select a part).

Representative modules per source (source, map name, reaction count).

Extraction, identity and selection

  • Cut: in-repo Escher community cutter (parity-tested); Stage B diagram/geometry windows for Reactome, WikiPathways, Human-maps, Metabolism Regulation, PANTHER and iCH360; BRENDA’s own extractor.
  • Deduplicate: core families and geometric variants; Stage B near-nested dedupe (nest_factor=2).
  • Canonical ids: BiGG, MetaNetX and/or Rhea where a unique crosswalk exists.
  • Provenance: source, map, licence and an extraction block (method, version, parameters, counts).
  • Selection: coverage ranks first; among same-source biochemical matches with the same reaction set, the denser drawing is kept.

Worked examples: docs/atlas_data_management.md#worked-examples · data/README.md.

2. Layout optimisation algorithm

Matching and curated reuse

Reactions are matched to Atlas modules (EC currentisation, Rhea metabolite scoring, name normalisation, weighted Jaccard, vicinity propagation). Report curated, topology-only and optional EC suggestions as separate rates in reaction_provenance.json. EC similarity extension is off by default (CLI --ec). Matched geometry is kept as drawn; the rest uses layout_style=curated (Bézier). Orthogonal libavoid remains CLI --layout-style legacy only. Details: docs/reaction_map_matching.md · docs/methodology.md.

Layout stages

After matching, the Composer keeps curated blocks rigid, completes uncovered reactions, orients free reactions, composes stray components, draws Bézier connections and places labels. Small models take the full path; mid-size models use a global plan then the same curated Bézier pass; larger models keep a skeleton and draw ~50-reaction views on demand. Each stage lists the layout targets it optimises in the README §2 table: rigid skeleton and matching keep curated-structure continuity; instances and composition/peripherals shorten long lines and cofactor clones and place exchange on the periphery, aspect and blank space; orientation sets participant placement; spacing/relaxation and Bézier connections (with the quality gate) reduce connection crossings, unrelated overlaps, detours, hooks and bends.

Determinism: fixed layout seed 20261105 (core.SEEDS), ELK/fCoSE seeds, PYTHONHASHSEED=0 on re-exec. Displacement measured by evaluate --compare-map only. compose --previous OpenMetaMaps_<stem>_result.json pins matched nodes and grafts leftovers.

Known gaps (docs/limitations.md): 2D component packing, harder orientation (incl. transporters), compartment-aware packing, stronger currency/biomass handling, crossing-aware composition acceptance, compose seed flag. Experimental off by default: OPM_REGIONS, OPM_LOWCONF, whole-block OPM_BLOCK_RELOC.

3. Evaluation criteria

Compose writes layout_quality into layout_issues.json / report.json; python3 project.py evaluate adds layout-rules metrics. Metric groups and status table: README §3. Details: docs/layout_evaluation.md.

Layout targets (including backlog) stay on Detailed metrics; non-targets under Debug (including main flow-direction share).

Rules and status (README §3): avoid crossings, overlaps and long lines, place participants consistently, aspect / compactness, reproducibility, build on previous layout and scale to GEMs are partial; respect compartments, compartment packing, axis-aligned segments and axes, grid metabolites, chain turns and cycle placement are not yet optimised.

Outputs

  • Reaction provenance: curated (community layout), topology-only suggestion, functional (EC) suggestion, bridge or generated, with matching evidence
  • Download formats: OpenMetaMaps_<name>_result.{json,sbgn,sbml,celldesigner.xml,svg,png} (Escher JSON, SBGN-ML, SBML Layout, CellDesigner, SVG, PNG)
  • Layout quality · Generation settings · Licensing metadata (licenses.json)

Integrity check: all reactions drawn; stoichiometry and compartments unchanged.
